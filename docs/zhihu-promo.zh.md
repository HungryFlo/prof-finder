# 找导师别再海投碰运气：我们做了一个「本机运行」的 PhD 导师匹配助手

> 开源仓库：[github.com/HungryFlo/prof-finder](https://github.com/HungryFlo/prof-finder)  
> 定位：帮助学生寻找潜在 PhD / MPhil 导师的本地工具  
> 口号：Your Ideal Professor Awaits.

找导师这件事，很多人卡在同一处：**经历写不细、名单筛不完、套磁写得空**。Prof-Finder 不是替你申请的中介，而是把「沉淀经历 → 建立画像 → 添加教授 → 运行匹配 → 生成邮件」收成一条可操作的工作流，而且默认跑在你自己的电脑上。

下面分两部分：前半给准备申请的同学；后半给关心怎么做出来的开发者。内容以当前仓库代码为准。

---

# 第一部分：给申请者 —— 它帮你做什么？

## 产品在解决什么

打开应用后，首页进度条就是五步（与界面文案一致）：

1. **沉淀经历** — 脑暴、聚类、细化，并取材生成文书素材  
2. **建立画像** — 上传简历，可选绑定信息池  
3. **添加教授** — Scholar、DBLP 或院校名单导入  
4. **运行匹配** — 在本机做语义相似度排序推荐  
5. **生成邮件** — 结合画像与信息池经历起草联络信  

副标题也写得很直白：**从经历沉淀到导师匹配**。

## 1. 信息池：先把经历想清楚

很多套磁写不好，不是文笔问题，是**素材不够细**。信息池按四个阶段工作：

| 阶段 | 你在做什么 |
|------|------------|
| **脑暴** | 写下与学术相关的经历线索，太碎也没关系；支持逐条添加或批量粘贴 |
| **聚类** | 把线索拖进看板分组，或标成独立项（手动整理，不是一键「AI 乱分」） |
| **细化** | 按字段补过程：缘起、过程、结果、问题、挫折、知识、洞见、自由补充等 |
| **文书** | 勾选已细化的故事，生成简历条目 / 个人陈述 / 研究计划 / 套磁片段等草稿，并可应用到画像 |

一个账号可以建多个信息池（不同方向、不同申请季各一份）。建议：**先细化故事，再完善画像、再匹配、再写信**——后面几步会明显更像你本人。

## 2. 学生画像：把材料变成「可匹配」的科研描述

创建画像时可以：

- 上传 `.md` / `.txt` / `.tex` 等简历；  
- 填写研究兴趣、个人陈述、研究计划、自由备注；  
- **绑定一个信息池**，把细化过的经历带进画像生成；  
- 选择是否用 LLM 抽取背景字段。

生成后会有面向匹配的学术画像正文，以及可编辑的技能、教育、科研、项目等。若已有学术画像，还能打开 **AI 对话打磨**：边聊边补充，再一键「优化画像」写回。

匹配只用你设为 **已激活** 的那一份画像。

## 3. 教授库：把候选导师攒成可管理的名单

界面里常见添加方式：

- **Google Scholar 链接** — 粘贴主页 URL，后台抓取；  
- **DBLP 链接** — 粘贴作者页，适合计算机方向书目；  
- **院校名单爬取** — 配置院系列表页，用 LLM 抽取或 CSS 选择器抽取，后台批量导入；  
- **手动添加** — 姓名、单位、主页、研究标签等。

导入后还可以做富化：补论文、生成论文摘要、生成教授科研画像、爬个人主页、关联 Scholar / DBLP 等。耗时操作走后台任务，右上角任务面板能看进度，不用干等。

## 4. 智能匹配：按研究方向「像不像」排序

首次匹配需下载本地嵌入模型 **Qwen3-Embedding-0.6B**（约 1.2 GB，从 ModelScope 下载到你选的数据目录）。之后：

- 确认有激活画像、教授列表不为空；  
- 点「运行匹配」；  
- 得到按匹配度排序的列表，并带上可读的匹配理由标签。

这不是「分数高就一定录取」，而是帮你**缩小要认真读主页、认真写信的名单**。最终仍要靠你读论文、看招人信息。

## 5. 生成邮件：草稿，不是代发

在匹配结果里点开教授，可按中文 / 英文生成联络信草稿。系统会尽量结合你的画像、教授侧信息、匹配理由，以及绑定信息池里的经历细节。

**务必人工审阅后再发送。** AI 不知道你的真实语气和教授近期是否招人。

## 为什么强调「本机运行」

便携版从 [GitHub Releases](https://github.com/HungryFlo/prof-finder/releases) 下载解压即可用，不必自己装 Python / Node。首次启动选择数据目录：数据库、设置、日志和嵌入模型都落在你指定的文件夹里。

- 默认只在本机监听，用浏览器打开本地页面；  
- LLM 能力用你自己的 API Key（OpenAI 兼容或 Anthropic，例如 DeepSeek 等），Key 存在本地数据库，接口返回时会脱敏；  
- 简历、教授名单、匹配结果不经过「我们的云端存档」；  
- 用完可用卸载脚本清理应用目录、数据目录和模型目录。

需要联网的部分主要是：你配置的 LLM、Scholar / DBLP / 院校网页、以及首次下模型。匹配算分本身在本地跑。

## 适合谁 / 不适合谁

适合：候选名单已经很长，不知道优先联系谁；套磁总是空话，需要把项目细节和教授方向对齐；想把整理材料、筛导师、写信放在同一套工具里。

不适合期待：一键保证录取、替代读论文、自动群发套磁。**它是助手，不是中介。**

下载与操作：仓库 Releases + 应用内「使用帮助」。

# 第二部分：给开发者 —— 设计取舍与实现亮点

以下对应仓库现状（FastAPI + Vue 3），强调「为什么这样做」。

## 1. 本地优先，而不是又一个云端匹配 SaaS

**形态**：桌面式本地应用（`prof-finder-launcher` 起 uvicorn，绑 `127.0.0.1`，自动开浏览器）+ Web UI；数据在用户选定目录的 SQLite。

**原因**：申请材料与 API Key 敏感；嵌入模型体积不小，适合本机缓存复用；爬虫 / LLM / 匹配都是长任务，本机进程更好控。

**代价**：要做 PyInstaller 便携包、首次 `/setup` 选目录写 `install.json`、路径校验与卸载脚本；开放注册的实例若暴露公网需自行加固。

## 2. 界面结构 = 领域工作流

侧边栏与首页五步对齐：信息池 → 画像 → 教授 → 匹配 → 设置 / 写信。路由、任务类型、帮助文案共用同一套心智模型，避免「功能菜单堆砌、用户不知道先点哪」。

## 3. 长任务：SqliteHuey + SSE，故意不引入 Redis

爬取、下模型、全量匹配、写信都是分钟级。实现要点：

- **Huey `SqliteHuey`**：队列落本地 DB，便携部署零外部中间件；  
- **进程内 Consumer**：与 API 同进程，适合单机工具；  
- **统一任务注册表**：二十余种任务类型，前端一个任务面板；  
- **SSE 进度**：`EventSource` 订阅，支持取消 / 中断后恢复 / 失败重试；  
- 重启后对「跑到一半」的任务标为 interrupted，而不是静默瞎重跑。

对桌面式工具，Redis / Celery 往往是过度基础设施。

## 4. 学生侧：结构化字段、语义画像、经历故事分层

- **解析 / 生成**：材料 + 可选信息池 → `profile-generate`，产出 `academic_profile` 等；  
- **对话精炼**：流式 chat + `profile-refine` 任务写回；  
- **信息池**：脑暴种子 → 手动聚类 → 故事字段 → 文书草稿；写信与画像可引用池内故事摘要。

匹配用的文本优先吃学术画像与分析字段，再拼技能 / 经历 / 项目——避免「解析出一堆 JSON 字段就直接当 query」。

## 5. 教授侧：多源互补 + 可配置爬虫

| 源 | 角色 |
|----|------|
| Google Scholar | 主页抓取与引用侧信息（scholarly） |
| DBLP | 稳定书目与 PID 导入 |
| 通用院校爬虫 | Crawl4AI；列表页可用 LLM 抽取或 CSS 选择器 |
| 富化管线 | 论文摘要、科研画像、主页爬取、Scholar/DBLP 关联匹配 |

产品上把「院校批量」定位为加速建池，并与 Scholar / DBLP 富化衔接，而不是唯一真相来源。请求延时可配，自动富化可关以省 API 费用。

## 6. 匹配：本地小嵌入模型，而不是每次让 LLM 打分

Web 匹配走 `SemanticMatcher`：

- 模型：**Qwen3-Embedding-0.6B**（1024 维），`sentence-transformers`，CUDA / MPS / CPU；  
- 非对称编码：教授当 document，学生画像用 `prompt_name="query"`；  
- 文本：教授优先 `research_profile` + 主题分析 + 前几篇论文摘要；学生优先学术画像与分析字段；  
- 分数：L2 归一化后点积（即余弦）映射到 0–100；  
- 教授向量可缓存，避免每次全量重算。

相对「让 LLM 给每位教授打分」更稳、更便宜、可离线复跑；相对纯关键词更能抓住表述不同但方向相近的情况。教授科研画像质量会直接传导到匹配质量——这也是自动富化开关存在的原因。

## 7. LLM：Provider 抽象 + 可测工作流层

- 用户级配置：`openai`（兼容接口）或 `anthropic`；Key / Base URL / 模型名可覆盖部署默认；  
- `ai_workflows`：无 DB、无 HTTP 的纯函数工作流，便于单测与复用；  
- 业务覆盖：画像生成与精炼、简历相关解析、论文摘要、教授科研画像、套磁信、信息池文书草稿、LLM 模式院校抽取等。

套磁信显式消费：激活画像、教授信息、匹配理由、写信语言，以及信息池故事摘要。产品文案坚持人工审阅，工程上也不做自动群发。

## 8. 工程上几个务实选择

- **前端**：Vue 3 + TypeScript + Naive UI；AI 对话区局部用 Tailwind / shadcn-vue 组件，主体不重写。  
- **双语与主题**：vue-i18n 中英；明暗色；匹配页可选写信语言。  
- **多用户本地隔离**：JWT；业务表按 `user_id` 过滤；任务与 SSE 校验归属。  
- **便携分发**：GitHub Actions 打 Windows / macOS 包；模型不打进安装包，首次按需下载。  
- **CLI**：Typer 提供 profile / professor / match / letter 等入口，适合脚本化与调试（与 Web 路径能力不完全等同，以 API/UI 为主路径）。

## 9. 刻意没做什么

- 不做默认的云端多租户匹配订阅——本地优先是产品原则。  
- 不做免审自动群发套磁——信誉与合规成本高于功能爽感。  
- 不把 Redis / K8s 当默认依赖——目标用户是申请季学生和本机跑的开发者。  

这些「不做」和「做了什么」一样，决定了仓库长什么样。
